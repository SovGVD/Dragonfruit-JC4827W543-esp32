# JC4827W543 resistive touchscreen

This checkout defaults to the ESP32-S3 JC4827W543 **resistive** module:
NV3041A QSPI display, XPT2046 touch, 4 MB flash and 8 MB octal PSRAM.
ROM loading uses the SD slot. The ROM is separate from the ESP32 application.

The display and SD wiring follows the local `esp32-pipboy` reference. Resistive
wiring and orientation follow the board's
[XPT2046 example](https://github.com/profi-max/JC4827W543_4.3inch_ESP32S3_board/blob/main/Examples/Demo_VSCode_Platformio/LVGL_Widgets_DMA/src/touch.h).
The register settings follow Arduino_GFX 1.4.9; see [notices](third-party-notices.md).

| Device | Signal | GPIO |
| --- | --- | --- |
| NV3041A, SPI3 | CS / CLK / D0 / D1 / D2 / D3 | 45 / 47 / 21 / 48 / 40 / 39 |
| Display | Backlight, active high | 1 |
| SD, SPI2 at 10 MHz | CS / CLK / MISO / MOSI | 10 / 12 / 13 / 11 |
| XPT2046, SPI2 at 2 MHz | CS / IRQ | 38 / 3 |
| XPT2046 | CLK / MISO / MOSI, shared with SD | 12 / 13 / 11 |
| BOOT button | Palm power key, active low | 0 |

Both SPI2 chip-selects are driven high before the first SD command. The bus
stays initialized across card unmounts. Touch uses a separate SPI device at its
own clock rate. If a card rejects enabling optional SPI data CRC (CMD59),
mount retries using ESP-IDF's CRC-off mode. Cards that support CRC keep it
on. During runtime SD operations the input task is parked. GPIO38
is touch CS on the resistive module; it must never be pulsed as GT911 reset.

## Prepare the SD card

Use a FAT32 card. Copy a supported ROM to its root as `palm.rom`: Palm IIIx 3.1,
Palm IIIx/V 4.1, or Palm IIIc 4.1. Virtual expansion storage requires OS 4.
The m125 and m515 ROMs require unsupported DragonBall VZ hardware.
The existing loader checks size and reset vectors, reads the ROM into PSRAM,
then unmounts the card. Missing SD, missing ROM and invalid ROM produce an LCD
message and halt until reset. No mount operation formats the card.

```text
palm.rom       required, supplied by you; no ROM is included
palm.cfg       optional; copy palm-jc4827w543.cfg.example here
install/       optional PRC/PDB/PQA files installed after Palm OS boots
backup/        optional database backups, managed through the UART console
palm-card/     Palm OS 4 virtual expansion card; created automatically
```

## Persistent Palm RAM and SD applications

The JC4827W543 now exposes **4 MB Palm RAM** (previously 2 MB). This is separate
from the board's 8 MB PSRAM, which also holds the ROM, video RAM and temporary
installer buffers. Installed applications and active card applications share
this RAM. With Palm OS 4, `/palm-card` on the physical SD is also presented as a
virtual VFS expansion volume; see below.

RAM persistence is enabled by default. The firmware checks for a matching
checkpoint after reading `palm.rom`, restores it, and warm-boots Palm OS.
Installed applications, database contents and RAM-backed preferences survive
ESP32 resets and power cycles. This is not an exact CPU/screen resume.

Two files are maintained in the SD root, named
`palm-<ROM-CRC>-4096K-ram.0` and `.1` (4 MB plus a 32-byte header each).
ROM contents, RAM size, header and payload checksums are verified. A damaged
newest slot falls back to the older valid slot. Saves write the inactive slot
and flush/sync it before promotion. Keep the FAT card healthy: this protects
against an interrupted file write, not arbitrary damage to the card/filesystem.
Different ROMs have different checkpoint filenames.

Automatic saves happen only when Palm enters sleep (BOOT or Palm auto-off).
There are no timed saves during active Palm use. Before unplugging,
**hold BOOT for one second** to put Palm to sleep and wait for the serial
`RAM checkpoint: saved/restored` log or the **RAM SAVED / SAFE TO POWER OFF**
screen (SD saves can take tens of seconds).
Changes after the last successful save can be lost if power is cut.

The JC display shows save/restore stages with a percentage and progress bar.
Percentages apply to the current stage: checking save 1/2, reading from SD,
checking RAM or writing to SD. Mounting and finalizing show `PLEASE WAIT`
because they have no measurable byte count. `KEEP POWER ON` stays visible
until the operation finishes. `RAM SAVED` appears only after flush, sync,
close and release of the save's SD reference; it remains on screen while Palm sleeps. Explicit console saves
while awake briefly show completion and return to Palm. Restore shows `RAM RESTORED`
before booting Palm; failures show an error and preserve the previous save.
These overlays use separate display buffers and never enter saved Palm RAM.
The user confirmed restore/save progress and the completion screen are visible
on the connected board after upload. Host checks also verify progress ordering
and that a failed or unchanged save never reports a completed write.

Optional `palm.cfg` settings:

```ini
state.enabled = 1
```

The former `state.autosave_seconds` setting is ignored. `state.enabled=0` starts with fresh RAM
and does not overwrite checkpoints. If existing checkpoint files are unreadable
or both fail validation, the firmware logs the problem, cold-boots and disables
saving for that session to preserve the files. Back them up/remove them to
start over. Removing both files for a ROM resets that ROM's saved Palm state.

To install applications, create `/install` in the SD root and put compatible
`.prc`, `.pdb` and `.pqa` files directly inside it, then reset the board. New
databases are installed after Palm boots. Same-named databases already present
in restored RAM are **kept**, including edited data; source files may stay on
the SD. Updating a same-named app requires explicitly removing it in Palm OS,
saving that change, then restarting with its replacement in `/install`.
The boot queue accepts up to 16 files, 512 KB per file and 1 MB total source
images. These are staging limits; installed apps and data share Palm's 4 MB,
and applications still must support the emulated CPU, OS and display.

UART0 commands `state save` and `state status` request/report a checkpoint.
The existing `backup`/`restore` commands export/import individual Palm databases
and remain useful independently of whole-RAM checkpoints. Native USB carries
logs but does not accept these commands.

Host reproduction uses the same file format and warm-boot path:

```sh
build-host/dragonfruit -r /path/to/palm.rom --state /tmp/palm-ram -c 400000000
python3 tools/test-palm-persistence.py build-host/dragonfruit /path/to/palm.rom
```

## Storage inside Palm OS (OS 4)

Virtual storage is enabled by default on JC4827W543. Use the working IIIx/V 4.1
or IIIc 4.1 ROM. The emulator provides the VFS/Expansion Manager trap interface
that these upgrade ROMs omit, and registers their documented feature flags.
No additional Palm driver PRC or different device ROM is required. Palm OS 3.1
continues to boot but has no virtual card; `/install` and RAM persistence still work.

The directory `/palm-card` becomes the root of a volume named **SD Card** inside
Palm. Firmware creates its standard directories without replacing existing files:

```text
palm.rom
palm.cfg
palm-card/
  PALM/
    Launcher/     compatible .prc apps and their bundled databases
    Programs/     documents and other data for VFS-aware applications
    Backup/       destination available to Palm backup applications
```

Put an app at `/palm-card/PALM/Launcher/Snake.prc`, start Palm and select **SD Card**
in the launcher's category menu at the top right. These files are separate from
`/install`: they remain on the virtual card until launched or explicitly copied.
Palm copies a card-launched app into its RAM, runs it, and removes that temporary
copy when returning to the launcher. Applications still need enough free Palm
RAM and must support this OS, CPU and display. Older apps may require their data
in RAM; VFS-aware apps can read and write documents directly on the card.

The firmware uses only `/palm-card` for guest paths. ROMs, checkpoints and the
firmware's `/install` and `/backup` directories are outside that volume. Host
paths, traversal and symbolic links are rejected. Formatting and low-level SD
commands are not exposed. Current limits are 8 simultaneous file/directory
handles and 1 MiB per database import/resource chunk. Volume size/free-space
reports are capped by Palm's 32-bit API. Advanced filesystem control, filesystem
driver installation, default-directory customization, changing dates/attributes
or the volume label, and imports/exports with custom progress callbacks return
an unsupported-operation error.

File contents, seek/resize, directory enumeration/create, rename/delete, file
metadata reads, PRC/PDB metadata/resource/record reads and database import/export
of RAM databases are supported. Writes occur when Palm apps request them; whole-RAM checkpoints
remain sleep-only. Writable files are synced on close and before reporting
**RAM SAVED / SAFE TO POWER OFF**. Emulated resets close all guest handles.
Keep the card inserted while powered. The filesystem stays mounted so open Palm
files remain valid, with reference-counted mounts for checkpoint/backup callers.
SD and resistive touch arbitrate their shared SPI bus through ESP-IDF.

Optional `palm.cfg` settings:

```ini
card.enabled = 1
card.read_only = 0
```

Use `card.read_only=1` to expose an existing `/palm-card` without allowing Palm
writes. Use `card.enabled=0` to disable virtual storage.

Host use and checks (ROMs and the optional Snake app stay local):

```sh
build-host/dragonfruit -r /path/to/OS4.rom --card /tmp/my-palm-card --ui
ctest --test-dir build-host --output-on-failure
build-host/test_palm_card /tmp/test-card /path/to/OS4.rom /path/to/Snake_123.prc
python3 tools/test-palm-persistence.py build-host/dragonfruit /path/to/OS4.rom --card
```

The no-ROM test covers the actual 68k trap calling convention, file round trips,
directory enumeration, read-only mode, path containment and stale handles. With
a ROM it also checks feature registration, Palm-allocated resource handles,
PRC import/export and warm reset. With Snake it drives setup and the normal
launcher, verifies the active application and removal of its transient RAM copy
after exit. Visual artifacts are written beside the temporary card directory.

The host defaults to 4 MB too; configure `-DPALM_RAM_MB=2` for the legacy RAM
capacity. The integration check creates its own test databases and verifies
installation, restart/restore, preserving an existing database when the SD
source changes, adding a new database, the reported RAM capacity and fallback
after truncating the newest checkpoint. No ROM or personal data is bundled.

Validated on 2026-10-16: all nine host tests pass. The real-ROM integration
check passes with IIIx 3.1, IIIx/V 4.1 and IIIc 4.1, with `MemCardInfo` reporting
4,194,304 bytes. Separate host installs of Checkers and Snake 123 also succeed
(application gameplay was not tested). On the connected JC4827W543 with the
IIIc 4.1 ROM, the firmware allocated 4096 KB RAM and restored a matching SD
checkpoint. The user confirmed their newly created memo survived the restart
and initial stylus setup was skipped. Checkpoint validation/loading on this
card added about 18 seconds to startup. Physical SD app installation still
requires putting the desired application files in `/install`.

The default layout is portrait with the USB connector at the bottom. The Palm
LCD is rendered at its native 160×160 pixels (1:1), with the native 160×60
Graffiti/silkscreen strip directly below it. No enlargement is applied. In native 480×272 panel coordinates the content is
rotated clockwise; display and touch use the same 1:1 transform.
The combined 160×220 portrait surface is centered on the physical panel.
Invalid layout settings fall back to this layout. The earlier side-by-side
layout is available as `preset=jc4827w543-landscape`.


## Build

Use ESP-IDF 6.0, matching the project's Docker toolchain. On Linux with Docker:

```sh
./tools/build-jc4827w543.sh
```

This builds under your user ID and creates:

- `build-jc4827w543/dragonfruit-jc4827w543.bin`: combined bootloader, partition
  table and application, flash at **0x0**.
- `build-jc4827w543/dragonfruit.bin`: application only, flash at **0x10000**.
- `build-jc4827w543/flasher_args.json`: chip, offsets and flash settings.

With an activated ESP-IDF environment, the equivalent application build is:

```sh
idf.py -B build-jc4827w543 -D IDF_TARGET=esp32s3 \
  -D SDKCONFIG=sdkconfig.jc4827w543 \
  -D SDKCONFIG_DEFAULTS=sdkconfig.defaults.jc4827w543 build
```

`CONFIG_TOUCH_XPT2046=y` is the resistive default. When reusing an old generated
config that selected capacitive touch, select **Dragonfruit board → JC4827W543
touchscreen → Resistive** in `idf.py ... menuconfig`, or regenerate that
sdkconfig from the supplied defaults. The tracked defaults do not overwrite an
explicit selection already saved in a generated sdkconfig.

## Flash

With the board connected and esptool 5 installed on the host:

```sh
python -m esptool --chip esp32s3 --port /dev/ttyACM0 --baud 460800 \
  write-flash 0x0 build-jc4827w543/dragonfruit-jc4827w543.bin
```

Replace the port with your board's port. Windows can use:

```powershell
./flash.ps1 -BuildDir build-jc4827w543 -Port COM5 -Monitor
```

The PowerShell flasher reads the chip and offsets from build metadata. Its
monitor is a host serial monitor, not a device acceptance test. If the board is
not entering its bootloader automatically, hold BOOT, press and release RESET,
then release BOOT to flash. After flashing, reset normally with the prepared SD
card inserted.

## Calibrate resistive touch

The starting raw ranges are 200–3900 on both axes. They are not measurements of
your individual panel. Copy [the example](../palm-jc4827w543.cfg.example) to the
SD root as `palm.cfg`. Set `touch.log_raw = 1`, reboot, and touch the corners.
The serial log reports raw ADC values, pressure and mapped panel coordinates.
Raw logging is throttled to one update per 200 ms during contact; touches in
unused space are also logged for calibration.

- `touch.swap_xy`: 0 or 1. Apply axis swapping first if movement follows the
  wrong axis. Min/max values refer to the axes after this swap.
- `touch.x_min`, `touch.x_max`, `touch.y_min`, `touch.y_max`: raw endpoints in
  0–4095, with minimum strictly below maximum.
- `touch.invert_x`, `touch.invert_y`: 0 or 1. Reverse the corresponding pixel
  axis after mapping. Both axes are inverted by default, verified from captured calibration
  taps on the connected resistive board.
- `touch.pressure_min`: 1–4095; default 400. Raise it to reject light/noisy
  contacts or lower it if light touches are missed.
- `touch.log_raw`: 0 or 1; disable it after calibration.

For each axis, record the lower and upper raw values reached near its physical
edges, then set inversion so the top-left corner maps near `panel=0,0` and the
bottom-right maps near `panel=479,271`. Reboot after edits. Invalid calibration
is rejected as a whole and uses the starting defaults. Out-of-range samples
are clamped to panel edges. Five samples per axis are median-filtered; the
first ADC conversion after switching drive axes is discarded. Pen release or
leaving a mapped region emits a pen-up event.

Palm OS's own first-boot digitizer wizard still runs after the physical panel
mapping; complete it with the stylus normally.

Hold BOOT for one second while running to toggle Palm sleep/wake. Reset and
BOOT are different buttons. ESP32 light sleep is disabled in this profile so
the BOOT polling and serial console remain available when Palm OS auto-sleeps.

## Console and current limits

UART0 is the existing debug console and serial HotSync transport (115200 baud
for the console). Native USB Serial/JTAG also carries boot/log output via the
secondary console. Native USB is **not** a HotSync bridge or a command-input
transport in this firmware. Use a UART0 connection for commands; `serial.mode`
now defaults to `wifi` on this board, routing Palm serial PPP internally to
Wi-Fi while UART0 stays a console. Existing SD configuration overrides this
default. See [PPP Wi-Fi setup](wifi.md) for Palm settings and the browser portal.
Use `serial.mode=console` to leave Wi-Fi inactive, or `auto` for the physical
UART0 serial bridge, and restart after changing the mode.
The `power` console command can wake Palm
OS, and the backup/restore commands remain available without M5 side buttons.

The S3 runs the 68000 interpreter. The original ESP32 JIT memory backend is not
validated for S3 and is not used. Battery voltage sensing is disabled because
there is no verified divider configuration; the emulated battery stays full.

## ROM compatibility

The established working target is Palm IIIx / Palm OS 3.1. A ROM passing the
loader's size and reset-vector checks is not a compatibility guarantee.

`Palm-III-4.1-en.rom` was reproduced stuck at the boot logo on both the
connected board and the unchanged host core. The supplied image is 1,736,704
bytes, with card-header CPU flags `0x0010` (MC68328) and HAL ID `rcky` (Palm III).
This project currently models the Palm IIIx / MC68EZ328 hardware instead.
[Cloudpilot's device definitions](https://github.com/cloudpilot-emu/cloudpilot-emu/blob/master/src/cloudpilot/emulator/EmDevice.cpp)
and [ROM-header parser](https://github.com/cloudpilot-emu/cloudpilot-emu/blob/master/src/cloudpilot/emulator/EmROMReader.cpp)
confirm that these are distinct hardware profiles.

The immediate boot loop repeatedly calls `KeyBootKeys`: the IIIx Port D input
values make the Palm III ROM see a permanently pressed boot key. A temporary
host-only probe releasing the Palm III key inputs reached the first Setup
screen. That probe was not applied to the firmware and does not validate Palm
III timers, interrupts, input, sleep, or applications. This ROM remains
unsupported pending a proper device profile and runtime verification.

## Verification

```sh
cmake -S src/host -B build-host
cmake --build build-host -j 4
ctest --test-dir build-host --output-on-failure
```

Host checks cover layout bounds and source/input round-trips, resistive
calibration, SD bus ownership/retries/remounts, ROM loading and cleanup, plus
the existing GT911-config and JIT-cache tests. Driver boundary tests use mocks.
The ESP-IDF build verifies compilation, linking and partition fit. Neither
proves a physical SD mount, XPT2046 electrical operation, panel orientation,
Palm ROM boot or stylus accuracy. Those require the actual module and ROM.

### Connected-board check, 2026-10-16

Uploaded with esptool to the connected ESP32-S3 revision 0.2. Flash contents
were hash-verified. The boot log confirms the 8 MB PSRAM memory test passed,
the display driver initialized at 480×272, and a 1,212,416-byte `palm.rom` was
read successfully from the inserted SD card. The emulator started and produced
framebuffer updates. Resistive pen-release events reached Palm OS's event trap.

Device bring-up exposed a card rejecting CMD59 and an unsupported finite SPI
bus-acquisition timeout. The firmware now retries card initialization without
optional data CRC on that rejection and uses `portMAX_DELAY` for touch bus
acquisition. The latter error is absent from the updated boot capture. The user confirmed Palm OS is visible and stylus events are responsive;
calibration initially looped because the hardware Y axis mirrored portrait
Palm X. Captured top-left `(838,3378)` and bottom-right `(2474,616)` ADC
samples now have regression coverage. After uploading the corrected portrait build, the user confirmed that Palm OS
calibration completes. This establishes physical calibration acceptance for
the connected board; broader application and Graffiti checks remain separate.

The default was subsequently changed to native 1:1 portrait pixels at the
user's request. The verified hardware axis correction is retained; only the
shared display/input layout scale and centering changed.
